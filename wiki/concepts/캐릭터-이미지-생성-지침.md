# 캐릭터 이미지 생성 지침

향후 모든 캐릭터 스프라이트 제작 후 공통 검토와 목현 v2의 통과·미통과 현황은 [[캐릭터-에셋-검수-현황]]에서 관리한다.

## 1. 목적과 적용 범위

캐릭터 모션을 바꿔도 크기와 위치가 튀지 않고, 게임에서 바로 불러 재생할 수 있는 스프라이트를 만든다. 주인공과 모든 적의 신규 제작·수정·시트 패킹·내보내기에 적용한다. 배경 풍경이나 UI에는 적용하지 않는다.

- **이미지 생성 도구를 사용하지 않는다.** 캐릭터 원화와 모든 모션 프레임은 Aseprite 작업 파일에서 직접 제작한다.
- **최종 산출물은 PixiJS 스프라이트시트 규격(3.3)이다.** PixiJS `Assets.load`로 바로 파싱되는 PNG 1장·JSON 1개가 아니면 완료본이 아니다.

캐릭터 시트의 크기·간격·투명도·검수에 관한 과거 지침과 충돌하면 이 문서를 적용한다. 새 규격은 제작 목표이며 기존 파일의 규격이나 게임 적용 상태를 소급 변경하지 않는다.

## 2. 제작 전에 고정할 항목

- 캐릭터별 승인된 대기 포즈를 외형 기준 이미지로 정하고 모든 모션에 같은 기준을 사용한다. 얼굴·머리 크기·몸통 비율·의상·색·무기 길이를 기록한다.
- 주인공과 적을 **같은 2.5등신 SD 비율과 같은 귀여운 페인터리 그림체**로 제작한다. 머리부터 발끝까지의 키가 머리 높이의 약 2.5배가 되도록 하고, 적도 5등신 이상의 성인 체형·작은 머리·사실적인 장신 비율로 만들지 않는다. 화면상의 크기 차이가 필요하면 캐릭터 전체를 같은 비율로 확대·축소하며 머리만 줄이지 않는다.
- 적의 위협감은 키 비율을 바꾸는 대신 표정, 흉터, 체격의 폭, 갑옷·의상, 무기, 자세로 표현한다. 적도 귀여운 SD 실루엣을 유지하되 성격과 역할은 구분되게 한다.
- 주인공과 적의 선 굵기·윤곽 처리·명암 단계·채색 밀도·색감·얼굴 표현을 동일한 페인터리 무협 스타일로 맞춘다. 한쪽만 도트화하거나, 사실적 성인 일러스트·다른 렌더링 기법으로 바꾸지 않는다. 승인된 주인공 대기 이미지와 적 대기 이미지를 나란히 놓고 그림체와 머리/몸 비율을 먼저 검수한다.
- 주인공만 전투 화면 왼쪽에서 오른쪽을 바라본다. 모든 적은 화면 오른쪽에서 왼쪽을 바라본다. 적을 좌우 반전해 방향 오류를 숨기지 않는다.
- 프레임 내부에서도 주인공의 캐릭터 중심축은 왼쪽, 적의 중심축은 오른쪽에 고정한다. 주인공은 오른쪽 공격 공간을, 적은 왼쪽 공격 공간을 확보한다. 이는 단순히 그림의 왼쪽/오른쪽 끝을 맞추는 정렬이 아니라 캐릭터의 고정 루트 기준점을 맞추는 정렬이다.
- 제작 목록, 프레임 수, 셀 크기, 기준점, 기준 신체 크기를 먼저 확정한다. 수치를 Aseprite 작업 파일과 PixiJS JSON에 동일하게 기록한다.

### 현재 캐릭터 세트

| 캐릭터 | idle | attack1 | attack2 | death |
| --- | ---: | ---: | ---: | ---: |
| 목현 / 혈랑채 두목 | 6 | 9 | 9 | 8 |
| 혈랑채 졸병 / 궁수 / 정예산적 | 6 | 9 | 9 | 8 |

캐릭터당 모든 모션을 파일 1개에 담아(3.2) 총 5파일·20모션·160프레임이다. 공격은 준비·가속·타격·회수·복귀를, 사망은 균형 붕괴·무기 낙하·착지·홀드를 각각 구분한다. 다른 캐릭터는 별도 기획에 따라 확정한다.

## 3. 신규 최종 시트 제작 기준

| 항목 | 규격 |
| --- | --- |
| 제작 방법 | Aseprite에서 직접 제작. 이미지 생성 도구 사용 안 함 |
| 캐릭터 크기 | 3.1의 캔버스 기준 크기로 **처음부터 제작**: 공통 셀 768×768px, 대기 신체 높이 512px |
| 파일 | 캐릭터당 Aseprite 작업 파일 1개, 최종 PNG 1장·JSON 1개. 모든 모션을 태그로 구분 (3.2) |
| 작업 시트 | 모션별 1행, 9열(최대 프레임 수), 남는 셀은 완전 투명 |
| 최종 산출물 | **PixiJS v8 `Spritesheet` JSON(hash) + PNG**, 트림 패킹, 4096×4096px 이하 (3.3, 3.4) |
| 안전 여백 | 캐릭터·무기·궤적 모두 셀 네 변에서 최소 32px |
| 주인공 기준점 | (192,624) = (W×0.25,H×0.8125), 프레임 왼쪽 중심축 |
| 적 기준점 | (576,624) = (W×0.75,H×0.8125), 프레임 오른쪽 중심축 |
| 표시 배율 | 0.5 |
| 형식 | 실제 알파 채널이 있는 RGBA PNG |

### 3.1 캔버스에 맞춘 캐릭터 크기

캐릭터 크기는 원화 크기가 아니라 **전투 캔버스에 딱 맞게 보이는 표시 크기에서 역산해 지정하고, 그 크기로 제작한다.** 더 큰 그림을 만든 뒤 줄이는 방식을 쓰지 않는다.

**캔버스 실측값.** 전투 캔버스는 640×390px 논리 해상도이고, PixiJS가 기기 픽셀 배율에 맞춰 최대 2배(1280×780px)로 렌더링한다(`resolution: min(devicePixelRatio, 2)`). 바닥선은 y=312(높이 80%), 주인공 루트는 x=150, 적 루트는 x=490(거리 340px)이다. 상단 중앙의 사냥터 버튼은 y 약 8~50px을 차지한다.

| 항목 | 화면 표시(논리 px) | 제작·납품(px) |
| --- | --- | --- |
| 대기 신체 높이(머리~발) | 256 (캔버스 높이의 약 66%) | 512 |
| 공통 셀 | 384×384 | 768×768 |
| 주인공 루트(셀 안) | (96, 312) | (192, 624) |
| 적 루트(셀 안) | (288, 312) | (576, 624) |
| 안전 여백 | 16 | 32 |

- **제작 크기 = 표시 크기 × 2.** 캔버스 최대 렌더 배율 2배에서 텍스처 1px이 화면 1px이 된다. 이보다 크게 만들면 화면에 도달하지 않는 다운로드·GPU 메모리 낭비이고, 작게 만들면 고배율 기기에서 흐려진다.
- **셀이 캔버스 안에 들어온다.** 셀 세로 기준 81.25%에 루트를 두면 루트 위쪽 312px이 바닥선에서 캔버스 꼭대기까지와 같고, 아래쪽 72px도 캔버스 안이다. 주인공 셀은 캔버스 x 54~438, 적 셀은 x 202~586을 차지한다.
- **점유 범위(여백 제외).** 루트에서 앞쪽 544px, 뒤쪽 160px, 위쪽 592px, 아래쪽 112px(화면 표시로는 272·80·296·56px) 안에 몸·무기·궤적·쓰러짐을 모두 넣는다. 주인공 공격의 최대 도달점은 캔버스 x=422라서 적 루트와 68px 떨어진다(적도 대칭).
- **머리와 몸은 사냥터 버튼 아래에 둔다.** 대기 신체 256px이면 머리 끝이 y=56이다. 버튼 영역에는 무기 끝·공격 궤적만 잠깐 겹칠 수 있다.
- **공격 범위가 넘치면** 셀을 키우지 않고 포즈·무기 궤적의 폭을 줄인다. 셀은 캔버스 배치에서 나온 값이므로, 캔버스 크기·바닥선·루트 x가 바뀔 때만 이 표와 JSON·표시 배율을 함께 다시 계산한다.
- **적 체급 차이**는 셀 안에서 신체를 다르게 그리지 않고 표시 배율로 조정한다. 확대 후에도 머리·무기가 캔버스 상단 안에 있는지 실제 화면에서 확인한다.

목현 v2 런타임 시트는 이 규격보다 먼저 만든 에셋이다. 920×920px 셀(대기 신체 높이 약 527px)을 모션별 PNG·JSON 4쌍(Aseprite json-array 형식)으로 트림 패킹해 `PLAYER_SCALE` 0.5로 표시하며, 루트는 (269.5, 805)px·정규화 anchor는 (0.29297, 0.875)다. 신규 제작으로 교체할 때 768px 셀·캐릭터 단일 파일·PixiJS 규격으로 다시 만든다.

프레임 점유 범위는 대기 포즈가 아니라 **4모션 전체에서 발생하는 최대 공격 범위와 모든 자세의 점유 영역**으로 검수한다. 몸·무기·참격 궤적·머리카락·뒤로 젖힘·쓰러짐까지 고정 루트 기준의 합집합이 위 점유 범위 안에 들어가야 한다. 함께 제작하는 주인공·적 세트의 모든 모션과 모든 프레임에 같은 768×768 셀을 사용한다.

특정 모션만 큰 프레임으로 만들거나 특정 프레임만 축소해 억지로 넣지 않는다. 대기에도 공격과 동일한 빈 공간을 유지한다. 작업 파일에서 프레임별 크롭으로 여백을 없애지 않는다. 여백 제거는 3.4 트림 패킹으로 내보낼 때만 한다.

가로 25%/75%, 세로 81.25%는 캔버스 배치에서 역산한 기준점이다. 확정한 역할별 중심축과 지면 기준은 대기/공격1/공격2/사망 전부에서 바꾸지 않는다. 무기·궤적을 포함한 전체 바운딩 박스의 중앙이나 매 프레임 발의 최하단으로 기준점을 다시 계산하지 않는다. 몸통의 기울기·발걸음·쓰러짐은 같은 루트에 대한 의도된 자세 변화로 표현한다.

**파일 크기가 같다고 캐릭터 크기가 같은 것은 아니다.** 같은 캐릭터는 모든 모션에서 머리·몸통 기준 배율을 유지한다. 무기나 궤적까지 포함한 바운딩 박스를 같은 높이로 맞추지 않는다. 웅크림·쓰러짐에서 실제 차지하는 높이가 줄어드는 것은 정상이다. 포즈가 바뀌어도 월드 기준점이 이동하지 않아야 한다.

### 3.2 캐릭터당 1개 파일

한 캐릭터의 모든 모션은 **하나의 파일로 제작·납품**한다. 모션별로 파일을 나누지 않는다.

| 단계 | 파일 | 구성 |
| --- | --- | --- |
| 작업 | `<캐릭터>.aseprite` 1개 | 모션별 1행: 1행 idle, 2행 attack1, 3행 attack2, 4행 death. 9열×4행, 768px 셀이면 6912×3072px. 남는 셀은 완전 투명 |
| 최종 | `assets/sprites/character/<캐릭터>-sheet.png` 1장 + `<캐릭터>-sheet.json` 1개 | 3.3 PixiJS 규격, 32프레임을 태그 순서대로 트림 패킹 |

- Aseprite 태그 이름은 `idle`, `attack1`, `attack2`, `death`로 고정한다. 태그별 프레임 수가 2장의 캐릭터 세트 표와 일치해야 한다.
- 작업 중 뒤쪽에 프레임을 추가하면 앞 태그 범위가 함께 늘어날 수 있다. 내보내기 전에 모든 태그의 시작·끝 프레임을 확인한다.
- 최종 PNG는 모바일 WebGL에서 보장되는 최대 텍스처 크기인 **4096×4096px 이하**여야 한다. 768px 셀 32프레임을 격자로 두면 이 크기를 넘으므로 반드시 3.4 트림 패킹으로 내보낸다. 트림 후에도 넘으면 모션을 파일로 쪼개지 않고 궤적 범위·중복 프레임을 줄이거나 이 규격을 다시 검토한다.
- 모든 모션이 한 텍스처를 공유하므로 모션 전환 시 추가 로딩이 없고, 모션 간 배율·기준점 불일치를 한 파일에서 검수할 수 있다.

### 3.3 최종 산출물: PixiJS 스프라이트시트 규격

최종 JSON은 **PixiJS v8 `Spritesheet`가 그대로 파싱하는 hash 형식**으로 만든다. Aseprite 원본 JSON(json-array·json-hash), 모션별 JSON, 자체 형식은 중간 파일일 뿐 최종 산출물이 아니다.

예시(프레임·배열 일부 생략):

```json
{
  "frames": {
    "mokhyeon/idle/0": {
      "frame": { "x": 1, "y": 1, "w": 212, "h": 498 },
      "rotated": false,
      "trimmed": true,
      "spriteSourceSize": { "x": 104, "y": 128, "w": 212, "h": 498 },
      "sourceSize": { "w": 768, "h": 768 },
      "anchor": { "x": 0.25, "y": 0.8125 },
      "duration": 160
    }
  },
  "animations": {
    "idle": ["mokhyeon/idle/0", "mokhyeon/idle/1"],
    "attack1": ["mokhyeon/attack1/0"],
    "attack2": ["mokhyeon/attack2/0"],
    "death": ["mokhyeon/death/0"]
  },
  "meta": {
    "image": "mokhyeon-sheet.png",
    "format": "RGBA8888",
    "size": { "w": 2048, "h": 2048 },
    "scale": "1"
  }
}
```

| 필드 | 규칙 | PixiJS 동작 |
| --- | --- | --- |
| `frames`의 키 | `<캐릭터>/<모션>/<0부터 번호>`. 캐릭터 간 중복 금지 | 텍스처 전역 캐시의 키가 된다. 이름이 겹치면 다른 캐릭터 텍스처를 덮어쓴다 |
| `frame` | 최종 PNG 안의 잘린 영역 | 텍스처 영역 |
| `rotated` | 항상 `false`. 패킹 시 회전을 쓰지 않는다 | `true`면 90° 회전 복원 경로를 탄다 |
| `trimmed`·`spriteSourceSize`·`sourceSize` | `trimmed: true`, `sourceSize`는 768×768, `spriteSourceSize`는 셀 안 잘린 위치 | `Texture`의 `orig`(원래 셀)·`trim`(잘린 위치)으로 자동 복원 |
| `anchor` | 주인공 `{0.25, 0.8125}`, 적 `{0.75, 0.8125}`. 원래 셀 기준 | `texture.defaultAnchor`가 되어 `Sprite`·`AnimatedSprite` 생성 시 기본 anchor로 적용 |
| `duration` | 밀리초. 기존 게임 타이밍 또는 승인값 | PixiJS가 읽지 않는 추가 필드. 로더가 `sheet.data.frames[이름].duration`으로 `AnimatedSprite`의 프레임 `time`을 만든다 |
| `animations` | `idle`·`attack1`·`attack2`·`death` 4개, 재생 순서대로 | `sheet.animations[모션]` 텍스처 배열 |
| `meta.image` | JSON과 같은 폴더의 PNG 파일명 | JSON 기준 상대 경로로 PNG 자동 로드 |
| `meta.size` | 최종 PNG 실제 크기 | 검수용 |
| `meta.scale` | 문자열 `"1"` | 텍스처 해상도로 쓰인다. 다른 값이면 표시 크기가 바뀐다 |

**게임에서 쓰는 방법.**

```ts
type FrameWithDuration = SpritesheetFrameData & { duration: number };

const sheet = await Assets.load<Spritesheet>('/sprites/character/mokhyeon-sheet.json');
const idle = new AnimatedSprite(
  sheet.animations.idle.map((texture, i) => ({
    texture,
    time: (sheet.data.frames[`mokhyeon/idle/${i}`] as FrameWithDuration).duration,
  })),
);
idle.scale.set(0.5);
```

- 현재 로더(`BattleCanvas.tsx`의 `loadAnimSet`, `sprite.ts`의 `loadAnimatedSprite`)는 모션별 Aseprite json-array 파일을 직접 읽는다. 이 규격의 시트를 연결할 때 캐릭터 JSON 1개를 `Assets.load`로 읽어 `sheet.animations`로 모션을 만들도록 로더를 함께 수정한다. 목현 v2와 혈랑채 적의 기존 런타임 시트는 모션별 파일 구조다.
- Aseprite `ExportSpriteSheet` 결과에는 `animations`·프레임별 `anchor`·캐릭터 접두 프레임 이름이 없다. 내보낸 뒤 변환 단계에서 프레임 이름을 규칙대로 바꾸고, `frameTags`로 `animations`를 만들고, `anchor`·`meta.scale`을 채운다.
- **최종 검수:** 브라우저에서 `Assets.load`로 JSON을 읽어 `Spritesheet`로 파싱되는지 확인한다. `Object.keys(sheet.animations)`가 4개 모션과 같고, 모션별 텍스처 수가 캐릭터 세트 표와 같고, 모든 텍스처의 `orig`가 768×768이고 `defaultAnchor`가 역할별 값인지 확인한다.

### 3.4 트림 패킹과 프레임별 기준점

2D 게임은 크기가 제각각인 프레임을 쓰면서도 캐릭터가 흔들리지 않는다. 프레임마다 "캐릭터 위치에서 어디에 그릴지"라는 오프셋을 별도 데이터로 가지기 때문이다. 고정 셀 방식은 이 오프셋을 그림의 셀 안 위치로 미리 넣어 둔 것이며, 좌표가 맞으면 화면 결과는 두 방식이 같다.

| 항목 | 고정 셀 격자 | 트림 패킹 + 프레임별 복원 좌표 |
| --- | --- | --- |
| 기준점 | 셀 안 같은 좌표에 그림을 배치 | JSON이 프레임별 원래 셀 크기와 잘린 위치를 기록 |
| 검수 | 편집기에서 겹쳐 보기로 바로 확인 | 좌표 오류가 눈에 잘 띄지 않아 복원 검사 필수 |
| 텍스처 | 빈 여백이 많고, 가장 넓은 공격이 셀 크기를 결정 | 여백을 잘라 작다 |

**작업·검수는 고정 셀로 하고, 최종 산출물만 트림 패킹으로 내보낸다.**

1. 그림은 3.1의 공통 셀·루트 기준으로 Aseprite 작업 파일에서 그리고, 고정 셀 상태에서 GIF·기준점 검수를 마친다.
2. Aseprite `ExportSpriteSheet`로 캐릭터 파일 전체를 한 번에 내보낸다: `type=PACKED`, `trim=true`(프레임마다 여백 제거), `shapePadding=2`, `borderPadding=1`, 회전 없음, `dataFormat=json-hash`, `listTags=true`. 선형 필터로 축소 표시할 때 이웃 프레임 색이 번지지 않도록 간격을 둔다.
3. 내보낸 JSON을 3.3 PixiJS 규격으로 변환한다.
4. 모든 프레임을 JSON 좌표대로 빈 768px 셀에 붙였을 때 작업 시트의 해당 셀과 픽셀 단위로 같아야 한다. 이후 실제 게임에서 대기·공격·사망 전환 중 발 위치가 튀지 않는지 확인한다.
5. 기존 시트의 해상도를 줄여야 할 때는 투명 가장자리가 어둡게 번지지 않도록 premultiplied alpha(예: Pillow `RGBa`)로 리사이즈한다. 새 캐릭터는 3.1 크기로 처음부터 그리므로 리사이즈하지 않는다.

**기준점 계산.** 기준점은 발이 닿는 지면 y와 몸통 중심 x다. 몸통 중심은 무기·궤적·이펙트를 뺀 몸통의 무게중심이나 두 발 사이 중앙으로 구한다. 무기까지 포함한 바운딩 박스 중앙에 맞추면 팔을 뻗거나 칼을 휘두를 때 박스가 넓어져 캐릭터가 좌우로 흔들린다.

**게임에서 추출한 기존 시트를 분석할 때.** 게임 화면에서 추출해 늘어놓은 시트(예: 메탈슬러그 추출 시트)는 프레임별 오프셋과 동작 순서 데이터가 빠진 채 눈대중으로 정렬된 자료다. 균등 격자로 자르거나 박스 중앙에 맞추면 흔들리므로 다음 순서로 복원한다.

1. 가장자리와 이어진 배경색만 제거한다. 검정 배경이면 캐릭터 안쪽의 검은 외곽선을 지우지 않는다.
2. 연결된 픽셀 덩어리로 프레임 박스를 구한다. 떨어진 조각(총알·불꽃·먼지)은 가까운 프레임에 합치고, 이웃과 붙은 폭발처럼 크기가 비정상인 덩어리는 수동으로 나눈다.
3. 크기·색·실루엣으로 동작 묶음과 순서를 추정하고 사람이 확인한다.
4. 발 지면 y와 몸통 중심 x로 기준점을 계산하고, 이전 프레임과 머리·몸통을 겹쳐 가장 잘 맞는 위치로 보정한다. 발이 보이지 않는 폭발·사망 프레임은 앞 프레임 기준점을 이어받거나 수동으로 지정한다.
5. 고정 셀로 재패킹하고 정상·저속 GIF로 흔들림을 검수한다.

상용 게임에서 추출한 스프라이트는 저작권 대상이다. 기술 분석·참고용으로만 쓰고 게임 에셋에 넣지 않는다.

### 3.5 도트 스프라이트로 제작할 때

- 그림체 통일 원칙에 따라 주인공만 도트로 바꾸지 않는다. 도트를 채택하면 같은 전투 세트의 모든 캐릭터를 함께 전환한다.
- PixiJS 기본 선형 필터는 확대한 도트를 흐리게 만든다. 도트 텍스처에만 `texture.source.scaleMode = 'nearest'`를 적용하고, 페인터리 시트에는 적용하지 않는다.
- 화면 표시 크기(대기 신체 256px, 셀 384px)는 3.1과 같게 유지하고, 도트 제작 크기를 그 정수분의 1로 정해 2·3·4 같은 정수배로 표시한다(예: 신체 64px·셀 96px을 4배). 소수 배율은 화면의 픽셀 크기가 들쭉날쭉해진다.
- 알파는 0/255만 쓰고, 한 캐릭터의 모든 모션이 같은 팔레트를 공유한다.
- 페인터리 원화를 축소·감색해 만든 도트는 얼굴과 외곽선이 뭉개진다. 도트로 가면 도트 기준 이미지를 따로 그린다.
- 최종 산출물은 도트도 3.3 PixiJS 규격을 따르고, `sourceSize`·`anchor`는 도트 셀 기준으로 기록한다.

## 4. 모션 품질

- 대기: 시작과 끝이 자연스럽게 이어진다. 호흡 때문에 신체 전체가 확대·축소되지 않는다.
- 공격: 준비→공격→회복이 연결된다. 무기를 쥔 손과 손잡이 접점이 유지되고 칼날 길이가 변하지 않는다.
- 공격 궤적: 실제 무기 이동 방향에 맞는 효과를 포함한다. 이웃 프레임 침범, 무기와 분리된 엉뚱한 궤적, 과도한 광원 배경은 금지한다.
- 사망: 특히 1~3프레임의 무기 위치를 연속으로 검수한다. 잡기→놓기→낙하→착지 과정에서 칼이 사라지거나 순간적으로 뒤집히면 실패다. 마지막 프레임은 쓰러진 자세로 홀드할 수 있어야 한다.
- 칼날에 붕대·천·장식 끈을 추가하지 않는다. 손잡이의 감개와 칼날을 구분한다.
- 모션 연결: 대기→공격 준비→공격 정점→회복→대기가 자연스럽게 이어져야 한다. 사망 진입도 같은 축·신체 배율로 연결한다. 접속 프레임의 몸통·발·손·무기 위치를 비교해 크롭 오차로 인한 순간이동이 없는지 검수한다. 사망을 억지로 대기로 되돌려 루프시키지 않는다.

### 4.1 프레임별 고유 동작

프레임 수는 파일 개수가 아니라 **눈으로 구분되는 동작 단계의 수**다. 같은 그림을 복제하거나 거의 보이지 않는 수치만 바꿔 프레임 수를 채우지 않는다.

- 모든 프레임은 `대기`, `준비`, `가속`, `타격 직전`, `타격`, `후속`, `복귀`처럼 한 문장으로 설명할 수 있는 역할을 가진다.
- 연속된 두 프레임은 몸통 각도, 팔꿈치·손목·무릎 위치, 무기 각도·끝점, 무게 중심, 머리카락·옷자락 후속 동작 가운데 최소 두 항목이 달라야 한다.
- 캐릭터 전체의 단순 이동, 동일 비율 확대·축소, 미세한 회전, 픽셀 해시 차이만으로는 새 동작 프레임으로 인정하지 않는다. 루트 고정 기울기나 웅크림은 관절·무기 변화에 더하는 보조 수단으로만 사용한다.
- 앞뒤 키포즈를 그대로 한 장씩 더 넣지 않는다. 중간 프레임의 무기 끝점과 손 위치는 시간 순서상 두 키포즈 사이에 있어야 한다.
- 기존 포즈를 수정해 중간 프레임을 만들 때도 얼굴·의상·무기 형태는 고정하되, 팔·다리·몸통·무기의 실루엣은 실제로 다시 그린다.
- PNG 바이트나 해시가 서로 다른지는 중복 파일을 찾는 기계 검사일 뿐이다. 최종 판정은 실제 게임 배율과 GIF에서 사람이 동작 차이를 식별할 수 있는지로 한다.

### 4.2 9프레임 공격 구성

| 프레임 | 역할 | 반드시 보이는 변화 |
|---:|---|---|
| 1 | 대기 연결 | 기본 자세와 동일한 시작점 |
| 2 | 준비 | 무게 중심 이동, 무릎 굽힘, 검을 드는 손의 이동 |
| 3 | 최대 준비 | 검과 팔이 공격 반대 방향으로 가장 멀리 이동 |
| 4 | 가속 | 몸통이 공격 방향으로 전환되고 검 끝점이 3·5번 사이에 위치 |
| 5 | 타격 직전 | 전진 자세와 손목 회전이 명확함 |
| 6 | 타격 정점 | 최대 공격 범위와 가장 강한 궤적 |
| 7 | 후속 동작 | 타격 방향을 지나간 검·팔·옷자락의 관성 |
| 8 | 복귀 | 검과 팔이 대기 위치로 돌아오는 중간 자세 |
| 9 | 대기 복귀 | 1번과 자연스럽게 연결되는 종료점 |

1번과 9번은 루프 접속을 위해 같을 수 있다. 그 밖의 프레임은 서로 다른 동작이어야 한다. 특히 2·4·8번은 인접 키포즈를 복제하지 않고 준비·가속·복귀를 각각 보여줘야 한다.

### 4.3 재생 검수

1. 투명 배경의 프레임 배열을 같은 크기로 나란히 놓고 실루엣과 무기 끝점의 이동을 확인한다.
2. JSON의 실제 duration으로 GIF를 만들고 정상 속도와 2배 느린 속도로 각각 확인한다.
3. 게임의 실제 표시 배율로 축소해 320px 폭 화면에서 준비·타격·복귀가 구분되는지 확인한다.
4. 동일 프레임 해시, 거의 같은 알파 실루엣, 한 프레임만 튀는 크기·루트 이동을 자동 검사한다.
5. 기계 검사를 통과해도 정상 속도에서 정지하거나 두 번 반복해 보이는 구간이 있으면 해당 중간 프레임을 다시 그린다.

## 5. 투명 배경 처리

**모든 캐릭터 스프라이트는 처음부터 투명 레이어에 그린다.** Aseprite 작업 파일에 배경 레이어·바닥 그림·체크무늬·안내선을 두지 않고, 참고용 레이어는 내보내기 전에 숨긴다. 체크무늬·검정·흰색을 그려 넣은 RGB 이미지는 투명 이미지가 아니다. 파일 확장자와 미리보기만으로 통과시키지 않는다.

기존 이미지를 가져와 배경을 지워야 할 때는 원본을 보존한 별도 출력으로 수행하고, 그 단계에서 캐릭터를 재배치·리사이즈·재디자인하지 않는다.

회색/흰색 전체 삭제를 금지한다. 칼날·흰 의상·활시위·효과 중심부까지 지워질 수 있다. 외곽선 보호와 영역별 검수를 수행한다. **알파 채널 존재는 필요조건일 뿐, 투명 처리 품질의 증거가 아니다.** 반투명 궤적 안에 배경색이 섞였는지, 흰 효과가 뚫렸는지, 가장자리에 밝은 테두리가 남았는지도 확인한다.

## 6. 제작과 내보내기를 분리한다

1. 기준 외형을 고정하고 3.1의 768px 셀·512px 신체 크기로 캐릭터 Aseprite 작업 파일 1개를 만든 뒤, 우선 대기·가장 넓은 공격·사망 행을 시험 제작한다.
2. 외형·방향·연속성·투명도·캔버스 점유 범위를 검수한 뒤 같은 파일의 나머지 모션 행을 그린다.
3. 몸·무기·궤적이 안전 여백을 넘어 셀 경계에 닿으면 해당 포즈를 셀 안에서 다시 그린다. 이웃 셀로 넘친 그림은 사각형 좌표만 바꿔 분리할 수 없다.
4. 모든 프레임이 동일 신체 배율·기준점으로 고정 셀에 있는지 확인한다. 작업 파일에서 프레임을 내용에 맞게 잘라 서로 다른 크기로 두지 않는다.
5. 3.4 순서로 트림 패킹해 내보내고 3.3 PixiJS 규격 JSON으로 변환한다.
6. 캐릭터의 최종 PNG 1장과 JSON 1개를 PixiJS로 불러 실제 게임과 같은 스케일에서 모든 모션을 연속 재생한다.

## 7. 납품과 완료 판정

납품: Aseprite 작업 파일, 최종 PNG, PixiJS 규격 JSON, 사용한 기준 이미지/규격, 검수 결과. 파일 이름과 프레임 이름에는 동일한 캐릭터·모션 이름을 사용한다. JSON 필드는 3.3을 따른다. duration은 그림에서 추정해 확정하지 말고 기존 게임 타이밍 또는 별도 승인값을 따른다.

다음 항목을 모두 통과하기 전에는 “게임 적용 가능/완료”로 표시하지 않는다.

- [ ] 이미지 생성 도구 없이 Aseprite 작업 파일에서 제작했다.
- [ ] 최종 JSON이 3.3 PixiJS 규격이다. `Assets.load`로 `Spritesheet`가 파싱되고, `animations`가 `idle`·`attack1`·`attack2`·`death` 4개이며 모션별 텍스처 수가 캐릭터 세트 표와 같고, 모든 텍스처의 `orig`가 768×768·`defaultAnchor`가 역할별 값이다. 프레임 이름이 다른 캐릭터와 겹치지 않고 `rotated`가 모두 `false`, `meta.scale`이 `"1"`이다.
- [ ] 캐릭터의 모든 모션이 작업 파일 1개와 최종 PNG 1장·JSON 1개에 들어 있다.
- [ ] 작업 시트 크기가 9열×768px, 4행×768px과 일치한다. 최종 PNG는 4096×4096px 이하이며, 모든 프레임을 JSON 좌표로 셀에 복원한 결과가 작업 시트의 해당 셀과 픽셀 단위로 일치한다.
- [ ] 3.1 크기로 제작했다: 공통 셀 768×768px, 대기 신체 높이 512px, 루트 주인공 (192,624)·적 (576,624). 표시 배율 0.5에서 머리·몸이 사냥터 버튼 아래에 있고 몸·무기·궤적이 캔버스 밖으로 나가지 않는다.
- [ ] 주인공과 적이 모두 약 2.5등신 SD 비율이며, 적에게 5등신 이상의 성인 체형이 섞이지 않았다. 선·명암·채색·얼굴 표현을 나란히 비교해 같은 그림체임을 확인했다.
- [ ] 모든 프레임 수·방향·순서가 맞고 이웃 포즈가 섞이지 않는다.
- [ ] 시작·종료 접속 프레임을 제외한 모든 프레임이 서로 다른 역할과 실루엣을 가지며, 인접 프레임의 몸통·관절·무기 변화 중 최소 두 항목이 눈으로 구분된다.
- [ ] 공격 2·4·8번 프레임이 각각 준비·가속·복귀를 표현하며 인접 키포즈의 복제나 단순 전체 변형이 아니다.
- [ ] 공격 범위를 포함해 제작 세트의 모든 모션/프레임 셀 크기가 같고 안전 여백 32px가 완전히 투명하다.
- [ ] 주인공 왼쪽 축·적 오른쪽 축이 각자의 모든 모션에서 고정되며, 공격하지 않는 포즈에도 같은 공격 공간을 남겼다.
- [ ] 최종 PNG에서 캐릭터 밖 영역의 알파가 0이며, 프레임 사이에 배경 픽셀이 없다.
- [ ] 어두운색·밝은색·유채색 배경에 합성해 구멍, 테두리 잔상을 검사했다.
- [ ] 무기·의상·활시위·공격 궤적을 작업 파일과 확대 비교했다.
- [ ] 대기↔공격↔사망 전환에서 머리·몸통 배율과 기준점이 튀지 않는다.
- [ ] 실제 로더가 JSON의 `anchor`를 사용하며 납품 기준점과 일치한다.

작업 시트에서 모션 행 r(idle 0, attack1 1, attack2 2, death 3)의 c번째 프레임은 x=c×768, y=r×768, w=h=768이다. 최종 JSON의 프레임별 `anchor`는 주인공 (0.25,0.8125), 적 (0.75,0.8125)이다. 월드 좌표에는 이 루트 기준점을 연결한다. 셀 크기나 로더의 anchor만 바꾸지 말고 실제 그림의 기준점과 함께 일치시켜야 한다. 최종 PNG의 `frame` 좌표는 작업 격자를 따르지 않으며, `spriteSourceSize`·`sourceSize`로 같은 768px 셀에 복원된다. 목현 v2의 런타임 셀과 루트는 3.1에 기록한다.

상태는 **작업 파일 → 원화·모션 검수 → 패킹·PixiJS 변환 검수 → 게임 적용 검수**로 구분한다. 단순 파일 확보와 게임 적용을 혼용하지 않는다.

## 8. 기존 재생성본에 대한 주의

2026-09-12의 `output/sprite-regeneration/transparent/` 27장은 1774×887px이다. 4×2 명목 격자는 평균 443.5px이며, 이번 기본 목표와 다르다. 투명화 때 위치·크기를 바꾸지 않았으므로 일정한 간격·신체 배율로 패킹 완료된 자료가 아니다.

실측은 [구현 참고 명세](../../output/sprite-regeneration/IMPLEMENTATION-SPEC.md)와 [측정 JSON](../../output/sprite-regeneration/layout-measurements.json)을 참고한다. 이 지침 작성은 기존 PNG 재패킹이나 게임 연동 완료를 의미하지 않는다.
