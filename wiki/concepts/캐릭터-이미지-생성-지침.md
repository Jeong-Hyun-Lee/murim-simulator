# 캐릭터 이미지 생성 지침

향후 모든 캐릭터 이미지 생성 후 공통 검토와 목현 v2의 통과·미통과 현황은 [[캐릭터-에셋-검수-현황]]에서 관리한다.

## 1. 목적과 적용 범위

캐릭터 모션을 바꿔도 크기와 위치가 튀지 않고, 게임에서 바로 불러 재생할 수 있는 스프라이트를 만든다. 주인공과 모든 적의 신규 생성·재생성·배경 제거·시트 패킹·PixiJS 내보내기에 적용한다. 배경 풍경이나 UI에는 적용하지 않는다.

- **Aseprite를 사용하지 않는다.** 원화와 모션 프레임은 이미지 생성으로 만들고, 셀 정렬·트림·패킹·JSON 작성은 스크립트로 처리한다.
- **최종 산출물은 PixiJS 스프라이트시트 규격(3.3)이다.** PixiJS `Assets.load`로 바로 파싱되는 캐릭터별 PNG 1장·JSON 1개가 아니면 완료본이 아니다.

캐릭터 시트의 크기·간격·투명도·검수에 관한 과거 지침과 충돌하면 이 문서를 적용한다. 새 규격은 제작 목표이며 기존 파일의 규격이나 게임 적용 상태를 소급 변경하지 않는다.

## 2. 생성 전에 고정할 항목

- 캐릭터별 승인된 대기 포즈를 외형 기준 이미지로 정하고 모든 모션에 같은 기준을 사용한다. 얼굴·머리 크기·몸통 비율·의상·색·무기 길이를 기록한다.
- 주인공과 적을 **같은 2.5등신 SD 비율과 같은 귀여운 페인터리 그림체**로 생성한다. 머리부터 발끝까지의 키가 머리 높이의 약 2.5배가 되도록 하고, 적도 5등신 이상의 성인 체형·작은 머리·사실적인 장신 비율로 만들지 않는다. 화면상의 크기 차이가 필요하면 캐릭터 전체를 같은 비율로 확대·축소하며 머리만 줄이지 않는다.
- 적의 위협감은 키 비율을 바꾸는 대신 표정, 흉터, 체격의 폭, 갑옷·의상, 무기, 자세로 표현한다. 적도 귀여운 SD 실루엣을 유지하되 성격과 역할은 구분되게 한다.
- 주인공과 적의 선 굵기·윤곽 처리·명암 단계·채색 밀도·색감·얼굴 표현을 동일한 페인터리 무협 스타일로 맞춘다. 한쪽만 도트화하거나, 사실적 성인 일러스트·다른 렌더링 기법으로 바꾸지 않는다. 승인된 주인공 대기 이미지와 적 대기 이미지를 나란히 놓고 그림체와 머리/몸 비율을 먼저 검수한다.
- 주인공만 전투 화면 왼쪽에서 오른쪽을 바라본다. 모든 적은 화면 오른쪽에서 왼쪽을 바라본다. 적을 좌우 반전해 방향 오류를 숨기지 않는다.
- 프레임 내부에서도 주인공의 캐릭터 중심축은 왼쪽, 적의 중심축은 오른쪽에 고정한다. 주인공은 오른쪽 공격 공간을, 적은 왼쪽 공격 공간을 확보한다. 이는 단순히 그림의 왼쪽/오른쪽 끝을 맞추는 정렬이 아니라 캐릭터의 고정 루트 기준점을 맞추는 정렬이다.
- 생성 목록, 프레임 수, 셀 크기, 기준점, 기준 신체 크기를 먼저 확정한다. 수치를 프롬프트와 PixiJS JSON에 동일하게 기록한다.

### 현재 캐릭터 세트

모션을 부드럽게 보이도록 **모든 모션은 10~16프레임으로 생성한다.** 모션별 기본값은 아래와 같고, 범위 안에서 조정하면 캐릭터 JSON의 `animations`와 정렬 시트에 실제 수를 기록한다.

| 캐릭터 | idle | attack1 | attack2 | death |
| --- | ---: | ---: | ---: | ---: |
| 목현 / 혈랑채 두목 | 12 | 16 | 16 | 14 |
| 혈랑채 졸병 / 궁수 / 정예산적 | 12 | 16 | 16 | 14 |
| 허용 범위 | 10~16 | 10~16 | 10~16 | 10~16 |

기본값 기준 캐릭터당 58프레임, 5파일·20모션·290프레임이다. 캐릭터당 텍스처 1장에 담는다(3.2). 공격은 준비·가속·타격·후속·복귀를, 사망은 경직·균형 붕괴·무기 낙하·착지·홀드를 각각 구분한다(4.2). 다른 캐릭터는 별도 기획에 따라 확정한다.

**재생 시간은 늘리지 않는다.** 프레임 수를 늘려도 모션 전체 길이는 기존 게임 타이밍을 유지하고, 프레임당 시간을 나눠 부드럽게 만든다.

| 모션 | 전체 길이 | 기본 프레임 수 | 프레임당 `duration` |
| --- | ---: | ---: | --- |
| idle | 960ms | 12 | 80ms |
| attack1·attack2 | 720ms | 16 | 45ms |
| death | 1080ms | 14 | 마지막 홀드 프레임 360ms, 나머지 13프레임이 720ms를 나눠 약 55ms |

프레임 수를 범위 안에서 바꾸면 `duration = 전체 길이 ÷ 프레임 수`로 다시 계산한다(사망은 홀드 360ms를 뺀 뒤 나눈다). 전체 길이 자체를 바꾸려면 전투 코드의 공격 주기·쓰러짐 대기 시간과 함께 승인받는다.

## 3. 신규 최종 시트 제작 기준

| 항목 | 규격 |
| --- | --- |
| 제작 방법 | 이미지 생성으로 원화·프레임 생성, 스크립트로 셀 정렬·트림·패킹·JSON 작성. Aseprite 사용 안 함 |
| 캐릭터 크기 | 3.1의 캔버스 기준 크기로 **처음부터 생성**: 공통 셀 768×768px, 대기 신체 높이 512px |
| 프레임 수 | 모션당 10~16프레임 (기본 idle 12·attack1 16·attack2 16·death 14) |
| 정렬 시트 | 캐릭터당 PNG 1장. 모션별 1행, 16열(최대 프레임 수), 남는 셀은 완전 투명 |
| 최종 산출물 | 캐릭터당 **PixiJS v8 `Spritesheet` JSON(hash) 1개 + 텍스처 PNG 1장**, 트림 패킹, 4096×4096px 이하 (3.2~3.4) |
| 안전 여백 | 캐릭터·무기·궤적 모두 셀 네 변에서 최소 32px |
| 주인공 기준점 | (192,624) = (W×0.25,H×0.8125), 프레임 왼쪽 중심축 |
| 적 기준점 | (576,624) = (W×0.75,H×0.8125), 프레임 오른쪽 중심축 |
| 표시 배율 | 0.5 |
| 형식 | 실제 알파 채널이 있는 RGBA PNG |

### 3.1 캔버스에 맞춘 캐릭터 크기

캐릭터 크기는 원화 크기가 아니라 **전투 캔버스에 딱 맞게 보이는 표시 크기에서 역산해 지정하고, 그 크기로 생성한다.** 더 큰 원화를 만든 뒤 줄이는 방식을 기본으로 삼지 않는다.

**캔버스 실측값.** 전투 캔버스는 640×390px 논리 해상도이고, PixiJS가 기기 픽셀 배율에 맞춰 최대 2배(1280×780px)로 렌더링한다(`resolution: min(devicePixelRatio, 2)`). 바닥선은 y=312(높이 80%), 주인공 루트는 x=150, 적 루트는 x=490(거리 340px)이다. 상단 중앙의 사냥터 버튼은 y 약 8~50px을 차지한다.

| 항목 | 화면 표시(논리 px) | 생성·납품(px) |
| --- | --- | --- |
| 대기 신체 높이(머리~발) | 256 (캔버스 높이의 약 66%) | 512 |
| 공통 셀 | 384×384 | 768×768 |
| 주인공 루트(셀 안) | (96, 312) | (192, 624) |
| 적 루트(셀 안) | (288, 312) | (576, 624) |
| 안전 여백 | 16 | 32 |

- **생성 크기 = 표시 크기 × 2.** 캔버스 최대 렌더 배율 2배에서 텍스처 1px이 화면 1px이 된다. 이보다 크게 만들면 화면에 도달하지 않는 다운로드·GPU 메모리 낭비이고, 작게 만들면 고배율 기기에서 흐려진다.
- **셀이 캔버스 안에 들어온다.** 셀 세로 기준 81.25%에 루트를 두면 루트 위쪽 312px이 바닥선에서 캔버스 꼭대기까지와 같고, 아래쪽 72px도 캔버스 안이다. 주인공 셀은 캔버스 x 54~438, 적 셀은 x 202~586을 차지한다.
- **점유 범위(여백 제외).** 루트에서 앞쪽 544px, 뒤쪽 160px, 위쪽 592px, 아래쪽 112px(화면 표시로는 272·80·296·56px) 안에 몸·무기·궤적·쓰러짐을 모두 넣는다. 주인공 공격의 최대 도달점은 캔버스 x=422라서 적 루트와 68px 떨어진다(적도 대칭).
- **머리와 몸은 사냥터 버튼 아래에 둔다.** 대기 신체 256px이면 머리 끝이 y=56이다. 버튼 영역에는 무기 끝·공격 궤적만 잠깐 겹칠 수 있다.
- **생성 결과 크기가 다르면** 모션 행 전체를 한 번 같은 비율로 맞춘다. 프레임마다 따로 확대·축소하지 않는다. 투명 가장자리가 있는 이미지는 premultiplied alpha로 리사이즈한다(3.4).
- **공격 범위가 넘치면** 셀을 키우지 않고 포즈·무기 궤적의 폭을 줄여 다시 생성한다. 셀은 캔버스 배치에서 나온 값이므로, 캔버스 크기·바닥선·루트 x가 바뀔 때만 이 표와 JSON·표시 배율을 함께 다시 계산한다.
- **적 체급 차이**는 셀 안에서 신체를 다르게 그리지 않고 표시 배율로 조정한다. 확대 후에도 머리·무기가 캔버스 상단 안에 있는지 실제 화면에서 확인한다.

목현 v2 런타임 시트는 이 규격보다 먼저 만든 에셋이다. 920×920px 셀(대기 신체 높이 약 527px)·6·9·9·8프레임을 모션별 PNG·JSON 4쌍(json-array 형식)으로 트림 패킹해 `PLAYER_SCALE` 0.5로 표시하며, 루트는 (269.5, 805)px·정규화 anchor는 (0.29297, 0.875)다. 신규 제작으로 교체할 때 768px 셀·캐릭터 단일 텍스처·PixiJS 규격으로 다시 만든다.

프레임 점유 범위는 대기 포즈가 아니라 **4모션 전체에서 발생하는 최대 공격 범위와 모든 자세의 점유 영역**으로 검수한다. 몸·무기·참격 궤적·머리카락·뒤로 젖힘·쓰러짐까지 고정 루트 기준의 합집합이 위 점유 범위 안에 들어가야 한다. 함께 제작하는 주인공·적 세트의 모든 모션과 모든 프레임에 같은 768×768 셀을 사용한다.

특정 모션만 큰 프레임으로 만들거나 특정 프레임만 축소해 억지로 넣지 않는다. 대기에도 공격과 동일한 빈 공간을 유지한다. 정렬 시트에서 프레임별 크롭으로 여백을 없애지 않는다. 여백 제거는 3.4 트림 패킹으로 내보낼 때만 한다.

가로 25%/75%, 세로 81.25%는 캔버스 배치에서 역산한 기준점이다. 확정한 역할별 중심축과 지면 기준은 대기/공격1/공격2/사망 전부에서 바꾸지 않는다. 무기·궤적을 포함한 전체 바운딩 박스의 중앙이나 매 프레임 발의 최하단으로 기준점을 다시 계산하지 않는다. 몸통의 기울기·발걸음·쓰러짐은 같은 루트에 대한 의도된 자세 변화로 표현한다.

**파일 크기가 같다고 캐릭터 크기가 같은 것은 아니다.** 같은 캐릭터는 모든 모션에서 머리·몸통 기준 배율을 유지한다. 무기나 궤적까지 포함한 바운딩 박스를 같은 높이로 맞추지 않는다. 웅크림·쓰러짐에서 실제 차지하는 높이가 줄어드는 것은 정상이다. 포즈가 바뀌어도 월드 기준점이 이동하지 않아야 한다.

### 3.2 캐릭터당 텍스처 1장 (성능 기준)

한 캐릭터의 모든 모션은 **텍스처 PNG 1장과 PixiJS JSON 1개**로 납품한다. 모션별로 파일을 나누지 않는다. PixiJS에서 성능이 더 좋은 쪽이기 때문이다.

| 항목 | 캐릭터당 1장 | 모션별 4장 |
| --- | --- | --- |
| 네트워크 요청 | PNG·JSON 2개 | 8개 |
| 이미지 디코딩·GPU 업로드 | 1회 | 4회 |
| 패킹 효율 | 모든 프레임을 한 번에 배치해 빈 공간이 가장 적다 | 시트마다 가장자리·여분 공간이 따로 생긴다 |
| GPU 메모리 | 네 모션을 모두 쓰므로 합계가 같다 | 같다. 전투 중 모든 모션을 반복 재생해 지연 로딩 이득이 없다 |
| 드로우콜 | 텍스처 소스 1개 | PixiJS v8은 서로 다른 텍스처도 한 배치에 여러 장(GPU 한도, 보통 16장 안팎) 묶으므로 이 화면에서는 차이가 거의 없다 |
| 주의점 | 최대 텍스처 크기 제한, 첫 업로드 1회가 크다 | 첫 공격·사망 재생 때 업로드 끊김이 생길 수 있다 |

- **텍스처 크기 상한.** 최종 PNG는 모바일에서 안정적으로 쓸 수 있는 **4096×4096px 이하**로 만든다. 768px 셀 58~64프레임을 격자로 두면 크게 넘으므로 반드시 3.4 트림 패킹으로 내보낸다.
- **프레임 수 예산.** 목현 v2 트림 시트의 프레임당 평균 점유 면적(여백·간격 포함)을 768px 셀로 환산하면 대기 약 11만 px², 공격 약 18만 px², 사망 약 19만 px²다. 기본 58프레임은 약 970만 px², 최대 64프레임은 약 1,050만 px²로 4096×4096(약 1,680만 px²)의 60% 안팎이다. 추정치이므로 실제 패킹 결과 크기로 상한을 확인한다.
- **2의 거듭제곱으로 늘리지 않는다.** PixiJS v8은 크기 제약이 없고, 4096×4096을 꽉 채우면 비압축 RGBA로 약 64MB다. 실제 패킹 크기 그대로 저장한다.
- **상한을 넘으면 모션별로 쪼개지 않는다.** 먼저 궤적 범위·중복 프레임을 줄이고, 그래도 넘으면 PixiJS 멀티팩(`meta.related_multi_packs`)으로 텍스처를 2장으로 나눈다. JSON 규칙과 `Assets.load` 한 번으로 불러오는 방식은 그대로다.
- **첫 재생 끊김 방지.** 로딩 단계에서 `pixi.js/prepare`의 `renderer.prepare.upload(sheet.textureSource)`로 텍스처를 GPU에 미리 올린다.
- **밉맵을 켜지 않는다.** 표시 배율 0.5가 고정이라 이득이 없고 GPU 메모리가 약 33% 늘어난다. PixiJS 기본값(`autoGenerateMipmaps: false`)을 유지한다.
- 한 텍스처에 모든 모션이 있으므로 모션 간 배율·기준점 불일치를 한 파일에서 검수할 수 있다.

| 단계 | 파일 | 구성 |
| --- | --- | --- |
| 생성 | 모션별 생성 결과 PNG | 한 번에 전체 시트를 만들기 어려우면 모션 행 단위로 생성해도 된다. 같은 기준 이미지·셀·루트를 쓴다 |
| 정렬 | `<캐릭터>-cells.png` 1장 | 모션별 1행: 1행 idle, 2행 attack1, 3행 attack2, 4행 death. 16열×4행, 12288×3072px. 남는 셀은 완전 투명. 검수용이며 게임에 넣지 않는다 |
| 최종 | `assets/sprites/character/<캐릭터>-sheet.png` 1장 + `<캐릭터>-sheet.json` 1개 | 3.3 PixiJS 규격, 모든 프레임을 모션 순서대로 트림 패킹 |

### 3.3 최종 산출물: PixiJS 스프라이트시트 규격

최종 JSON은 **PixiJS v8 `Spritesheet`가 그대로 파싱하는 hash 형식**으로 만든다. 모션별 JSON, json-array 형식, 자체 형식은 최종 산출물이 아니다. 패킹 스크립트가 이 형식을 직접 쓴다.

예시(프레임·배열 일부 생략):

```json
{
  "frames": {
    "mokhyeon/idle/0": {
      "frame": { "x": 1, "y": 1, "w": 212, "h": 498 },
      "rotated": false,
      "trimmed": true,
      "spriteSourceSize": { "x": 104, "y": 128, "w": 212, "h": 498 },
      "sourceSize": { "w": 768, "h": 768 },
      "anchor": { "x": 0.25, "y": 0.8125 },
      "duration": 80
    }
  },
  "animations": {
    "idle": ["mokhyeon/idle/0", "mokhyeon/idle/1"],
    "attack1": ["mokhyeon/attack1/0"],
    "attack2": ["mokhyeon/attack2/0"],
    "death": ["mokhyeon/death/0"]
  },
  "meta": {
    "image": "mokhyeon-sheet.png",
    "format": "RGBA8888",
    "size": { "w": 2048, "h": 2048 },
    "scale": "1"
  }
}
```

| 필드 | 규칙 | PixiJS 동작 |
| --- | --- | --- |
| `frames`의 키 | `<캐릭터>/<모션>/<0부터 번호>`. 캐릭터 간 중복 금지 | 텍스처 전역 캐시의 키가 된다. 이름이 겹치면 다른 캐릭터 텍스처를 덮어쓴다 |
| `frame` | 최종 PNG 안의 잘린 영역 | 텍스처 영역 |
| `rotated` | 항상 `false`. 패킹 시 회전을 쓰지 않는다 | `true`면 90° 회전 복원 경로를 탄다 |
| `trimmed`·`spriteSourceSize`·`sourceSize` | `trimmed: true`, `sourceSize`는 768×768, `spriteSourceSize`는 셀 안 잘린 위치 | `Texture`의 `orig`(원래 셀)·`trim`(잘린 위치)으로 자동 복원 |
| `anchor` | 주인공 `{0.25, 0.8125}`, 적 `{0.75, 0.8125}`. 원래 셀 기준 | `texture.defaultAnchor`가 되어 `Sprite`·`AnimatedSprite` 생성 시 기본 anchor로 적용 |
| `duration` | 밀리초. 기존 게임 타이밍 또는 승인값 | PixiJS가 읽지 않는 추가 필드. 로더가 `AnimatedSprite`의 프레임 `time`으로 쓴다 |
| `animations` | `idle`·`attack1`·`attack2`·`death` 4개, 재생 순서대로 | `sheet.animations[모션]` 텍스처 배열 |
| `meta.image` | JSON과 같은 폴더의 PNG 파일명 | JSON 기준 상대 경로로 PNG 자동 로드 |
| `meta.size` | 최종 PNG 실제 크기 | 검수용 |
| `meta.scale` | 문자열 `"1"` | 텍스처 해상도로 쓰인다. 다른 값이면 표시 크기가 바뀐다 |

**게임에서 쓰는 방법.**

```ts
import 'pixi.js/prepare';

type FrameWithDuration = SpritesheetFrameData & { duration: number };

const sheet = await Assets.load<Spritesheet>('/sprites/character/mokhyeon-sheet.json');
await app.renderer.prepare.upload(sheet.textureSource);
const idle = new AnimatedSprite(
  sheet.animations.idle.map((texture, i) => ({
    texture,
    time: (sheet.data.frames[`mokhyeon/idle/${i}`] as FrameWithDuration).duration,
  })),
);
idle.scale.set(0.5);
```

- 현재 로더(`BattleCanvas.tsx`의 `loadAnimSet`, `sprite.ts`의 `loadAnimatedSprite`)는 모션별 json-array 파일을 직접 읽는다. 이 규격의 시트를 연결할 때 캐릭터 JSON 1개를 `Assets.load`로 읽어 `sheet.animations`로 모션을 만들도록 로더를 함께 수정한다. 목현 v2와 혈랑채 적의 기존 런타임 시트는 모션별 파일 구조다.
- **최종 검수:** 브라우저에서 `Assets.load`로 JSON을 읽어 `Spritesheet`로 파싱되는지 확인한다. `Object.keys(sheet.animations)`가 4개 모션과 같고, 모션별 텍스처 수가 캐릭터 세트 표와 같고, 모든 텍스처의 `orig`가 768×768이고 `defaultAnchor`가 역할별 값인지 확인한다.

### 3.4 트림 패킹과 프레임별 기준점

2D 게임은 크기가 제각각인 프레임을 쓰면서도 캐릭터가 흔들리지 않는다. 프레임마다 "캐릭터 위치에서 어디에 그릴지"라는 오프셋을 별도 데이터로 가지기 때문이다. 고정 셀 방식은 이 오프셋을 그림의 셀 안 위치로 미리 넣어 둔 것이며, 좌표가 맞으면 화면 결과는 두 방식이 같다.

| 항목 | 고정 셀 격자 | 트림 패킹 + 프레임별 복원 좌표 |
| --- | --- | --- |
| 기준점 | 셀 안 같은 좌표에 그림을 배치 | JSON이 프레임별 원래 셀 크기와 잘린 위치를 기록 |
| 검수 | 나란히 놓거나 겹쳐 보기로 바로 확인 | 좌표 오류가 눈에 잘 띄지 않아 복원 검사 필수 |
| 텍스처 | 빈 여백이 많고, 가장 넓은 공격이 셀 크기를 결정 | 여백을 잘라 작다 |

**검수는 고정 셀 정렬 시트로 하고, 최종 산출물만 트림 패킹으로 만든다.**

1. 생성 결과를 3.1의 공통 셀·루트 기준으로 정렬 시트에 배치하고, 고정 셀 상태에서 GIF·기준점 검수를 마친다.
2. 패킹 스크립트가 캐릭터의 모든 프레임을 한 번에 처리한다: 프레임마다 알파 기준으로 여백을 잘라내고, 회전 없이 한 텍스처에 배치하며, 프레임 사이 2px·가장자리 1px 간격을 둔다. 선형 필터로 축소 표시할 때 이웃 프레임 색이 번지지 않도록 하기 위함이다.
3. 같은 스크립트가 3.3 PixiJS 규격 JSON을 쓴다.
4. 모든 프레임을 JSON 좌표대로 빈 768px 셀에 붙였을 때 정렬 시트의 해당 셀과 픽셀 단위로 같아야 한다. 이후 실제 게임에서 대기·공격·사망 전환 중 발 위치가 튀지 않는지 확인한다.
5. 이미지를 줄여야 할 때는 투명 가장자리가 어둡게 번지지 않도록 premultiplied alpha(예: Pillow `RGBa`)로 리사이즈한다.

**기준점 계산.** 기준점은 발이 닿는 지면 y와 몸통 중심 x다. 몸통 중심은 무기·궤적·이펙트를 뺀 몸통의 무게중심이나 두 발 사이 중앙으로 구한다. 무기까지 포함한 바운딩 박스 중앙에 맞추면 팔을 뻗거나 칼을 휘두를 때 박스가 넓어져 캐릭터가 좌우로 흔들린다.

**게임에서 추출한 기존 시트를 분석할 때.** 게임 화면에서 추출해 늘어놓은 시트(예: 메탈슬러그 추출 시트)는 프레임별 오프셋과 동작 순서 데이터가 빠진 채 눈대중으로 정렬된 자료다. 균등 격자로 자르거나 박스 중앙에 맞추면 흔들리므로 다음 순서로 복원한다.

1. 가장자리와 이어진 배경색만 제거한다. 검정 배경이면 캐릭터 안쪽의 검은 외곽선을 지우지 않는다.
2. 연결된 픽셀 덩어리로 프레임 박스를 구한다. 떨어진 조각(총알·불꽃·먼지)은 가까운 프레임에 합치고, 이웃과 붙은 폭발처럼 크기가 비정상인 덩어리는 수동으로 나눈다.
3. 크기·색·실루엣으로 동작 묶음과 순서를 추정하고 사람이 확인한다.
4. 발 지면 y와 몸통 중심 x로 기준점을 계산하고, 이전 프레임과 머리·몸통을 겹쳐 가장 잘 맞는 위치로 보정한다. 발이 보이지 않는 폭발·사망 프레임은 앞 프레임 기준점을 이어받거나 수동으로 지정한다.
5. 고정 셀로 재패킹하고 정상·저속 GIF로 흔들림을 검수한다.

상용 게임에서 추출한 스프라이트는 저작권 대상이다. 기술 분석·참고용으로만 쓰고 게임 에셋에 넣지 않는다.

### 3.5 도트 스프라이트로 제작할 때

- 그림체 통일 원칙에 따라 주인공만 도트로 바꾸지 않는다. 도트를 채택하면 같은 전투 세트의 모든 캐릭터를 함께 전환한다.
- PixiJS 기본 선형 필터는 확대한 도트를 흐리게 만든다. 도트 텍스처에만 `texture.source.scaleMode = 'nearest'`를 적용하고, 페인터리 시트에는 적용하지 않는다.
- 화면 표시 크기(대기 신체 256px, 셀 384px)는 3.1과 같게 유지하고, 도트 제작 크기를 그 정수분의 1로 정해 2·3·4 같은 정수배로 표시한다(예: 신체 64px·셀 96px을 4배). 소수 배율은 화면의 픽셀 크기가 들쭉날쭉해진다.
- 알파는 0/255만 쓰고, 한 캐릭터의 모든 모션이 같은 팔레트를 공유한다.
- 페인터리 원화를 축소·감색해 만든 도트는 얼굴과 외곽선이 뭉개진다. 최종 품질이 필요하면 도트 기준 이미지를 따로 만든다.
- 도트 생성 도구의 캔버스 크기(예: 64×64)는 캐릭터 키가 아니다. 결과의 실제 신체 높이를 재서 표시 배율을 정한다.
- 최종 산출물은 도트도 3.2 캐릭터당 텍스처 1장·3.3 PixiJS 규격을 따르고, `sourceSize`·`anchor`는 도트 셀 기준으로 기록한다.

## 4. 모션 품질

- 대기: 시작과 끝이 자연스럽게 이어진다. 호흡 때문에 신체 전체가 확대·축소되지 않는다.
- 공격: 준비→공격→회복이 연결된다. 무기를 쥔 손과 손잡이 접점이 유지되고 칼날 길이가 변하지 않는다.
- 공격 궤적: 실제 무기 이동 방향에 맞는 효과를 포함한다. 이웃 프레임 침범, 무기와 분리된 엉뚱한 궤적, 과도한 광원 배경은 금지한다.
- 사망: 특히 1~3프레임의 무기 위치를 연속으로 검수한다. 잡기→놓기→낙하→착지 과정에서 칼이 사라지거나 순간적으로 뒤집히면 실패다. 마지막 프레임은 쓰러진 자세로 홀드할 수 있어야 한다.
- 칼날에 붕대·천·장식 끈을 추가하지 않는다. 손잡이의 감개와 칼날을 구분한다.
- 모션 연결: 대기→공격 준비→공격 정점→회복→대기가 자연스럽게 이어져야 한다. 사망 진입도 같은 축·신체 배율로 연결한다. 접속 프레임의 몸통·발·손·무기 위치를 비교해 크롭 오차로 인한 순간이동이 없는지 검수한다. 사망을 억지로 대기로 되돌려 루프시키지 않는다.

### 4.1 프레임별 고유 동작

프레임 수는 파일 개수가 아니라 **눈으로 구분되는 동작 단계의 수**다. 같은 그림을 복제하거나 거의 보이지 않는 수치만 바꿔 프레임 수를 채우지 않는다.

- 모든 프레임은 `대기`, `준비`, `가속`, `타격 직전`, `타격`, `후속`, `복귀`처럼 한 문장으로 설명할 수 있는 역할을 가진다.
- 연속된 두 프레임은 몸통 각도, 팔꿈치·손목·무릎 위치, 무기 각도·끝점, 무게 중심, 머리카락·옷자락 후속 동작 가운데 최소 두 항목이 달라야 한다.
- 캐릭터 전체의 단순 이동, 동일 비율 확대·축소, 미세한 회전, 픽셀 해시 차이만으로는 새 동작 프레임으로 인정하지 않는다. 루트 고정 기울기나 웅크림은 관절·무기 변화에 더하는 보조 수단으로만 사용한다.
- 앞뒤 키포즈를 그대로 한 장씩 더 넣지 않는다. 중간 프레임의 무기 끝점과 손 위치는 시간 순서상 두 키포즈 사이에 있어야 한다.
- **프레임을 늘린 목적은 부드러움이다.** 늘어난 프레임은 키포즈 사이의 사이 프레임(in-between)으로 채운다. 무기 끝점·손·머리는 직선이 아니라 동작의 호(arc)를 따라 이동한다.
- **간격은 가감속을 따른다.** 준비 끝·타격 정점·복귀 끝처럼 동작이 멈추는 키포즈 앞뒤는 이동 간격을 좁게, 가속·타격 통과 구간은 넓게 둔다. 모든 사이 프레임을 같은 간격으로 나누지 않는다.
- 연속 프레임의 변화량이 줄어도 "최소 두 항목 변화" 규칙은 유지한다. 대신 한 프레임만 크게 튀는 변화(갑작스러운 무기 각도·신체 크기·루트 이동)가 없어야 한다.
- 원본 시트에서 기존 포즈를 수정해 중간 프레임을 만들 때도 얼굴·의상·무기 형태는 고정하되, 팔·다리·몸통·무기의 실루엣은 실제로 다시 구성한다.
- PNG 바이트나 해시가 서로 다른지는 중복 파일을 찾는 기계 검사일 뿐이다. 최종 판정은 실제 게임 배율과 GIF에서 사람이 동작 차이를 식별할 수 있는지로 한다.

### 4.2 모션별 프레임 구성

#### 공격(16프레임 기본)

| 프레임 | 구간 | 역할 | 반드시 보이는 변화 |
|---:|---|---|---|
| 1 | 시작 | 대기 연결 | 기본 자세와 동일한 시작점 |
| 2 | 준비 | 준비 시작 | 무게 중심이 뒤로 이동하기 시작 |
| 3 | 준비 | 준비 | 무릎 굽힘, 검을 드는 손의 이동 |
| 4 | 준비 | 최대 준비 직전 | 검과 팔이 공격 반대 방향으로 거의 끝까지 이동 |
| 5 | 준비 | **최대 준비(키포즈)** | 검·팔·몸통이 공격 반대 방향 끝에 도달 |
| 6 | 가속 | 가속 시작 | 몸통이 공격 방향으로 돌기 시작, 검 끝점은 5번 근처 |
| 7 | 가속 | 가속 | 몸통 전환이 명확하고 검 끝점이 6·8번 사이 중간 |
| 8 | 가속 | 타격 직전 | 전진 자세와 손목 회전이 명확함 |
| 9 | 타격 | **타격 정점(키포즈)** | 최대 공격 범위와 가장 강한 궤적 |
| 10 | 타격 | 타격 통과 | 검이 목표 방향을 지나가고 궤적이 흐려지기 시작 |
| 11 | 후속 | 후속 1 | 검·팔의 관성 이동이 멈추기 시작 |
| 12 | 후속 | 후속 2 | 옷자락·머리카락이 뒤따라 도착 |
| 13 | 복귀 | 감속 | 무게 중심이 루트 쪽으로 돌아오기 시작 |
| 14 | 복귀 | 복귀 1 | 검과 팔이 대기 위치로 절반쯤 돌아옴 |
| 15 | 복귀 | 복귀 2 | 대기 자세 직전, 옷자락 흔들림이 잦아듦 |
| 16 | 끝 | 대기 복귀 | 1번과 자연스럽게 연결되는 종료점 |

- 1번과 16번은 대기 접속을 위해 같을 수 있다. 그 밖의 프레임은 서로 다른 동작이어야 한다.
- 가속(6~8)과 타격(9~10) 구간은 간격을 넓게, 준비 끝(4~5)과 복귀 끝(14~15)은 간격을 좁게 둔다. 타격 정점은 한 프레임만 둬 타격감을 살린다.
- **10~15프레임으로 줄일 때**는 반드시 남길 9단계(대기 연결·준비·최대 준비·가속·타격 직전·타격 정점·후속·복귀·대기 복귀)에 가속 1장을 더한 10프레임에서 시작한다. 프레임을 추가할 때는 복귀 → 후속 → 준비 → 타격 통과 순서로 사이 프레임을 늘린다. 타격 정점은 늘리지 않는다.

#### 대기(12프레임 기본)

| 구간 | 프레임 | 역할 |
|---|---:|---|
| 들숨 | 1~4 | 어깨·가슴이 조금씩 올라가고 옷자락·머리 끈이 늦게 따라 움직임 |
| 정점 | 5~6 | 들숨 끝 정지에 가까운 느린 간격 |
| 날숨 | 7~10 | 어깨가 내려가고 무기 끝이 미세하게 흔들림 |
| 최저점 | 11~12 | 12번 다음 1번이 이어지도록 되돌아오는 자세 |

- 신체 전체를 확대·축소해 호흡을 표현하지 않는다. 어깨·가슴·옷자락·머리카락·무기 끝의 위치 변화로 표현한다.
- 10~16프레임 범위에서 들숨·날숨 구간을 같은 비율로 늘리거나 줄인다. 마지막 프레임 다음에 1번이 튀지 않아야 한다.

#### 사망(14프레임 기본)

| 구간 | 프레임 | 역할 |
|---|---:|---|
| 경직 | 1~2 | 피격 반동으로 몸통이 뒤로 젖혀짐 |
| 균형 붕괴 | 3~5 | 무릎이 꺾이고 무게 중심이 무너짐 |
| 무기 놓기 | 6~7 | 손이 펴지고 무기가 손에서 떨어지기 시작 |
| 낙하 | 8~10 | 몸과 무기가 각자 호를 그리며 떨어짐. 칼이 사라지거나 순간적으로 뒤집히지 않음 |
| 착지 | 11~12 | 몸이 바닥에 닿고 작은 반동 |
| 정지 | 13 | 반동이 가라앉음 |
| 홀드 | 14 | 쓰러진 자세 유지(360ms), 게임이 이 프레임을 멈춰 보여줌 |

- 10~16프레임 범위에서 낙하·착지 구간을 먼저 조정하고, 마지막 홀드 프레임은 항상 1장 유지한다.

### 4.3 재생 검수

1. 투명 배경의 프레임 배열을 같은 크기로 나란히 놓고 실루엣과 무기 끝점의 이동을 확인한다.
2. JSON의 실제 duration으로 GIF를 만들고 정상 속도와 2배 느린 속도로 각각 확인한다.
3. 게임의 실제 표시 배율로 축소해 320px 폭 화면에서 준비·타격·복귀가 구분되는지 확인한다.
4. 동일 프레임 해시, 거의 같은 알파 실루엣, 한 프레임만 튀는 크기·루트 이동을 자동 검사한다.
5. 기계 검사를 통과해도 정상 속도에서 정지하거나 두 번 반복해 보이는 구간이 있으면 해당 중간 프레임을 다시 만든다.
6. 프레임 사이 무기 끝점·손·머리 위치를 겹쳐 그려 이동 경로가 호를 이루고, 한 프레임만 크게 튀는 구간이 없는지 확인한다.

## 5. 투명 배경 처리

**모든 캐릭터 이미지의 배경은 반드시 제거한다.** 처음부터 투명 배경을 요청하고, 생성 결과에 배경이 남으면 제거와 윤곽선 검수를 마친 뒤에만 최종 시트로 사용한다. 배경이 있는 이미지는 생성 후보일 뿐 완료본이 아니다. 체크무늬·검정·흰색을 그려 넣은 RGB 이미지는 투명 이미지가 아니다. 파일 확장자와 미리보기만으로 통과시키지 않는다.

배경 제거는 원본을 보존한 별도 출력으로 수행한다. 배경 제거 단계에서는 캐릭터를 재배치·리사이즈·재디자인하지 않는다. 생성 도구가 외형이나 배치를 바꾸면 해당 결과는 폐기한다. 대체 처리 방식은 사용자의 승인과 사용 도구의 규칙을 따른다.

회색/흰색 전체 삭제를 금지한다. 칼날·흰 의상·활시위·효과 중심부까지 지워질 수 있다. 외곽선 보호와 영역별 검수를 수행한다. **알파 채널 존재는 필요조건일 뿐, 배경 제거 품질의 증거가 아니다.** 반투명 궤적 안에 체크무늬가 남았는지, 흰 효과가 뚫렸는지, 가장자리에 밝은 테두리가 남았는지도 확인한다.

## 6. 생성과 패킹을 분리한다

1. 기준 외형을 고정하고 3.1의 768px 셀·512px 신체 크기로 우선 대기·가장 넓은 공격·사망을 시험 생성한다.
2. 외형·방향·연속성·투명도·캔버스 점유 범위를 검수한 뒤 나머지 모션을 생성한다.
3. 생성 도구가 정확한 격자를 지켰다고 가정하지 않는다. 원본은 후보 자료로 보관한다.
4. 프레임끼리 겹쳤다면 해당 포즈를 독립 이미지로 재생성한다. 이미 겹친 그림은 사각형 좌표만 바꿔 분리할 수 없다.
5. 프레임별 소유 영역을 확인하고 동일 신체 배율·기준점으로 캐릭터 정렬 시트 1장의 고정 셀에 배치한다. 복원 좌표 없이 프레임을 내용에 맞게 잘라 서로 다른 크기로 납품하지 않는다.
6. 3.4 순서로 캐릭터 텍스처 1장에 트림 패킹하고 3.3 PixiJS 규격 JSON을 만든다.
7. 최종 PNG 1장과 JSON 1개를 PixiJS로 불러 실제 게임과 같은 스케일에서 모든 모션을 연속 재생한다.

## 7. 납품과 완료 판정

납품: 원본 후보, 정렬 시트, 최종 PNG, PixiJS 규격 JSON, 사용한 기준 이미지/규격, 검수 결과. 파일 이름과 프레임 이름에는 동일한 캐릭터·모션 이름을 사용한다. JSON 필드는 3.3을 따른다. duration은 그림에서 추정해 확정하지 말고 기존 게임 타이밍 또는 별도 승인값을 따른다.

다음 항목을 모두 통과하기 전에는 “게임 적용 가능/완료”로 표시하지 않는다.

- [ ] 최종 JSON이 3.3 PixiJS 규격이다. `Assets.load`로 `Spritesheet`가 파싱되고, `animations`가 `idle`·`attack1`·`attack2`·`death` 4개이며 모션별 텍스처 수가 캐릭터 세트 표와 같고, 모든 텍스처의 `orig`가 768×768·`defaultAnchor`가 역할별 값이다. 프레임 이름이 다른 캐릭터와 겹치지 않고 `rotated`가 모두 `false`, `meta.scale`이 `"1"`이다.
- [ ] 캐릭터의 모든 모션이 최종 PNG 1장·JSON 1개에 들어 있다. PNG는 4096×4096px 이하이고 2의 거듭제곱으로 늘린 빈 공간이 없다.
- [ ] 모든 모션이 10~16프레임이고, 모션 전체 길이가 기존 게임 타이밍(idle 960ms·attack 720ms·death 1080ms)과 같으며 프레임별 `duration` 합이 그 값과 일치한다.
- [ ] 정렬 시트 크기가 16열×768px, 4행×768px과 일치하며, 모든 프레임을 JSON 좌표로 셀에 복원한 결과가 정렬 시트의 해당 셀과 픽셀 단위로 일치한다.
- [ ] 3.1 크기로 생성했다: 공통 셀 768×768px, 대기 신체 높이 512px, 루트 주인공 (192,624)·적 (576,624). 표시 배율 0.5에서 머리·몸이 사냥터 버튼 아래에 있고 몸·무기·궤적이 캔버스 밖으로 나가지 않는다.
- [ ] 주인공과 적이 모두 약 2.5등신 SD 비율이며, 적에게 5등신 이상의 성인 체형이 섞이지 않았다. 선·명암·채색·얼굴 표현을 나란히 비교해 같은 그림체임을 확인했다.
- [ ] 모든 프레임 수·방향·순서가 맞고 이웃 포즈가 섞이지 않는다.
- [ ] 시작·종료 접속 프레임을 제외한 모든 프레임이 서로 다른 역할과 실루엣을 가지며, 인접 프레임의 몸통·관절·무기 변화 중 최소 두 항목이 눈으로 구분된다.
- [ ] 공격·대기·사망이 4.2 구간 구성을 따르고, 준비·가속·후속·복귀 사이 프레임이 인접 키포즈의 복제나 단순 전체 변형이 아니다. 무기 끝점·손·머리 이동이 호와 가감속 간격을 따라 부드럽게 이어진다.
- [ ] 공격 범위를 포함해 제작 세트의 모든 모션/프레임 셀 크기가 같고 안전 여백 32px가 완전히 투명하다.
- [ ] 주인공 왼쪽 축·적 오른쪽 축이 각자의 모든 모션에서 고정되며, 공격하지 않는 포즈에도 같은 공격 공간을 남겼다.
- [ ] 모든 캐릭터 PNG에서 배경이 제거됐고 실제 알파가 0인 영역이 있으며, 빈 셀과 프레임 사이에 배경 픽셀이 없다.
- [ ] 어두운색·밝은색·유채색 배경에 합성해 체크무늬, 구멍, 테두리 잔상을 검사했다.
- [ ] 무기·의상·활시위·공격 궤적을 원본과 확대 비교했다.
- [ ] 대기↔공격↔사망 전환에서 머리·몸통 배율과 기준점이 튀지 않는다.
- [ ] 로딩 단계에서 텍스처를 GPU에 미리 올려 첫 공격·사망 재생에 끊김이 없다.
- [ ] 실제 로더가 JSON의 `anchor`를 사용하며 납품 기준점과 일치한다.

정렬 시트에서 모션 행 r(idle 0, attack1 1, attack2 2, death 3)의 c번째 프레임은 x=c×768, y=r×768, w=h=768이다. 최종 JSON의 프레임별 `anchor`는 주인공 (0.25,0.8125), 적 (0.75,0.8125)이다. 월드 좌표에는 이 루트 기준점을 연결한다. 셀 크기나 로더의 anchor만 바꾸지 말고 실제 그림의 기준점과 함께 일치시켜야 한다. 최종 PNG의 `frame` 좌표는 정렬 격자를 따르지 않으며, `spriteSourceSize`·`sourceSize`로 같은 768px 셀에 복원된다. 목현 v2의 런타임 셀과 루트는 3.1에 기록한다.

상태는 **생성 후보 → 투명화 검수 → 패킹·PixiJS 변환 검수 → 게임 적용 검수**로 구분한다. 단순 파일 확보와 게임 적용을 혼용하지 않는다. 공통 재사용 프롬프트는 이 지침에 보존하고 개별 생성 큐의 완료된 일회성 프롬프트는 큐 정책을 따른다.

## 8. 재사용 생성 프롬프트


2026-09-12의 `output/sprite-regeneration/transparent/` 27장은 1774×887px이다. 4×2 명목 격자는 평균 443.5px이며, 이번 기본 목표와 다르다. 투명화 때 위치·크기를 바꾸지 않았으므로 일정한 간격·신체 배율로 패킹 완료된 자료가 아니다.
