# 무림인 키우기 — 캔버스 렌더링 기술스택 조사 보고서

(참고: 현재 리포지토리에는 아직 `package.json`이나 소스 코드가 없고 `docs/`, `wiki/` 문서만 존재함을 확인했다. 즉 기술 선택은 완전히 열려 있는 상태.)

## 1. 후보별 요약

### 1) Raw Canvas 2D API (프레임워크 없음)

- **특징**: `CanvasRenderingContext2D` + 직접 짠 `requestAnimationFrame` 루프. 스프라이트 그리기, 애니메이션 상태머신, 파티클 풀링을 전부 직접 구현.
- **적합도**: 이 게임의 전투 씬은 사실 매우 단순함(스프라이트 2개, 초당 수십 개 수준의 이펙트/텍스트 팝업). raw Canvas 2D로도 충분히 감당 가능한 범위.
- **장점**: 의존성 0, 번들 크기 0KB 추가, 디버깅이 직관적(블랙박스 없음), 완전한 제어권.
- **단점**: 스프라이트 배칭, 텍스처 아틀라스 관리, 파티클 풀링, 애니메이션 타임라인을 전부 손수 작성해야 함. 이펙트 개수가 늘어나면(수백 개 단위) 최적화(더티 리전, draw call 최소화)를 직접 신경 써야 함.
- **학습곡선/생태계**: 학습곡선은 낮음~중간. 생태계는 사실상 없음(라이브러리가 아니므로 커뮤니티 자산 재사용 불가).
- **성능 특성**: CPU 래스터라이즈 기반. 스프라이트 수가 적은 이 프로젝트 규모에서는 문제 없음.

### 2) PixiJS

- **특징**: WebGL(+ v8부터 WebGPU 렌더러 병행)을 쓰는 2D 렌더링 라이브러리. Scene graph(Container/Sprite/Ticker), 텍스처 배칭, 필터(블러/글로우), BitmapText, `@pixi/particle-emitter` 등 파티클 이펙트 전용 라이브러리 존재.
- **적합도**: "초당 다수의 이펙트(타격/파티클/크리티컬 텍스트)"라는 요구사항과 정확히 맞아떨어짐 — 대량의 작은 스프라이트를 GPU 배칭으로 저렴하게 그리는 것이 핵심 장점.
- **장점**: 배칭/텍스처 아틀라스가 내장되어 draw call이 최소화됨 → CPU 부담이 낮아 "항상 켜져 있는" 자동전투 루프에 적합. 다수의 방치형/가챠 게임이 실전 사용 중이라 검증된 선택지. TypeScript 지원 양호, 문서/커뮤니티 성숙, React 바인딩(@pixi/react) 존재.
- **단점**: WebGL 컨텍스트 관리, Container/Ticker 개념 학습 필요(얕은 학습곡선). 번들 크기 raw Canvas 대비 증가(코어만 써도 250~400KB 선, 트리쉐이킹으로 축소 가능).
- **학습곡선/생태계**: 낮음~중간. 생태계 성숙도 높음(Spine 애니메이션 연동 등).
- **성능 특성**: GPU 가속 배칭 렌더링이라 이펙트가 많아질수록 raw Canvas 2D 대비 여유가 큼. WebGL 컨텍스트가 유휴 시에도 계속 렌더링되므로 프레임 스킵/정지 최적화는 별도로 신경 써야 함.

### 3) Phaser 3

- **특징**: 물리엔진(Arcade/Matter), 씬 관리, 입력/오디오/타일맵/에셋 로딩 파이프라인까지 갖춘 풀스택 2D 게임 프레임워크.
- **적합도**: 낮음. 타일맵도, 물리 충돌도, 복잡한 레벨 구조도 필요 없음 — "스프라이트 2개가 붙어서 반복 모션" 요구사항 대비 명백한 오버스펙.
- **장점**: 풀패키지라 나중에 새 게임 기능(미니게임 등)이 생기면 빠르게 확장 가능. 커뮤니티/튜토리얼 매우 풍부.
- **단점**: Scene 생명주기(`preload/create/update`), 플러그인 시스템 등 개념이 많아 학습곡선 상대적으로 가파름. 번들 크기 큼(1MB 이상). 불필요한 물리/타일맵 모듈까지 따라옴.
- **학습곡선/생태계**: 중간~높음. 생태계는 매우 성숙하지만 이 프로젝트 규모엔 과함.

### 4) Konva.js (혹은 react-konva)

- **특징**: Canvas 2D(비-WebGL) 기반 scene graph 라이브러리. 도형/이미지에 대한 클릭/드래그/호버 이벤트가 내장되어 있어 인터랙티브 다이어그램·노드 그래프에 강점.
- **적합도**: 전투 렌더러로는 부적합(WebGL 가속이 없어 파티클 많은 씬엔 비효율적), 하지만 **성장보드(무공 트리)를 캔버스로 그리고 싶을 경우**엔 최적의 후보.
- **장점**: react-konva로 React state와 자연스럽게 연동. 노드 클릭 → 카드 팝업 같은 이벤트 처리가 매우 쉬움.
- **단점**: 전투 씬의 메인 렌더러로 쓰기엔 성능 특성이 안 맞음. 즉 "두 개의 별도 렌더링 기술(전투=Pixi, 성장보드=Konva)"을 쓰게 되어 기술스택이 늘어남.
- **학습곡선/생태계**: 낮음. 생태계는 안정적이나 PixiJS/Phaser보다 커뮤니티 규모는 작음(약 145KB 번들).

### 5) Three.js (2D 직교 투영)

- **특징**: WebGL 기반 3D 엔진을 직교 카메라로 2D처럼 사용.
- **적합도**: 매우 낮음. 순수 2D 게임에 3D 씬그래프 전체를 끌고 오는 셈 — 오버스펙.
- **단점**: 번들 크기 큼(600KB+), 보일러플레이트 많음, 러닝커브 가파름. 2D 전용 기능(스프라이트 배칭, 텍스트 렌더링)은 오히려 Pixi보다 불편함.
- **결론**: 참고용으로만 언급 — 이 프로젝트엔 권장하지 않음.

### 6) DOM/CSS + Canvas 하이브리드

- **특징**: 전투 연출만 캔버스(raw Canvas 2D 또는 PixiJS)로 그리고, 나머지 UI(HUD, 성장보드, 팝업/모달, 토스트)는 일반 DOM(React/Vue + CSS)으로 처리.
- **적합도**: 매우 높음 — "어떤 캔버스 라이브러리를 쓰는가"와 "하이브리드 구조로 갈 것인가"는 별개 축의 결정이며, 이 프로젝트는 후자를 채택하는 것이 사실상 필수에 가깝다(2장 참고).
- **장점**: DOM은 텍스트 레이아웃, 접근성, 호버/트랜지션, 폼/모달 등에서 압도적으로 개발 속도가 빠름. 캔버스는 "많은 작은 그래픽이 빠르게 반복되는" 전투 연출에만 집중 가능.
- **단점**: 레이어링(z-index, pointer-events) 설계를 잘못하면 클릭이 씹히거나 캔버스 밑 UI가 안 눌리는 문제 발생. 두 개의 렌더링 파이프라인(DOM reflow/repaint + 캔버스 rAF 루프)이 공존하므로 상태 동기화 설계가 필요.

## 2. 성장보드(무공 트리 UI) 렌더링 방식 비교

| 항목 | 캔버스로 그리기 (raw Canvas / Konva / Pixi) | DOM/HTML 오버레이 (div + SVG) |
|---|---|---|
| 노드 클릭 판정 | 직접 hit-test 구현 필요(Konva/Pixi는 이벤트 시스템 내장) | `<div onClick>` — 브라우저가 공짜로 처리 |
| 호버/잠금 상태 시각효과 | 매 프레임 수동으로 다시 그리거나 필터 적용 | CSS `:hover`, `transition`, `filter` — 선언적, GPU 합성 활용 |
| 카드 팝업 | 캔버스 위에 별도 DOM 팝업을 얹거나, 캔버스 안에 텍스트/버튼을 직접 그려야 함 | 일반 HTML 모달 컴포넌트 — 텍스트 줄바꿈, 스크롤, 폼 요소 전부 브라우저가 처리 |
| 접근성 | 캔버스 콘텐츠는 스크린 리더가 인식 불가(별도 ARIA 레이어 필요) | 기본적으로 접근성 트리에 노출됨 |
| 연결선(트리 엣지) | Graphics API로 직접 그리기 | SVG `<line>`/`<path>`로 간단히, CSS로 애니메이션 가능 |
| 대규모 노드(수백 개) 성능 | 캔버스가 유리(DOM reflow 비용 없음) | 노드가 아주 많아지면(수백~수천) DOM 레이아웃 비용 증가 가능 |
| 개발 속도(소규모 팀 기준) | 상대적으로 느림 — hit-test, 텍스트, 팝업을 다 손으로 | 빠름 — 익숙한 CSS/HTML 도구 그대로 사용 |
| 이 프로젝트 적용성 | 트리 규모가 수십~약 100개 노드 수준이면 캔버스 이점 미미 | 노드 수가 이 정도면 DOM 방식의 단점(성능)이 거의 드러나지 않음 |

**결론**: 성장보드는 자동전투처럼 "항상 렌더링이 도는" 화면이 아니라 열고 닫는 별도 화면이므로, DOM의 성능 약점(대량 reflow)이 실질적으로 문제되지 않는다. 반면 DOM의 강점(클릭 이벤트, 카드 팝업, 호버 트랜지션, 접근성)은 정확히 성장보드가 필요로 하는 것들이다. 따라서 **성장보드는 DOM(div 노드) + SVG(연결선) 조합으로 구현하는 것을 권장**한다. 노드 수가 향후 수백 개 이상으로 커지고 팬/줌까지 필요해지면 그때 Konva 같은 캔버스 기반 대안으로 전환을 고려한다.

## 3. HUD/UI 레이어링 정석 패턴

캔버스 위에 재화 스트립, 팝업, 토스트 같은 UI를 얹는 표준 아키텍처는 **"캔버스 = 배경 레이어, DOM = UI 레이어"** 로 나누는 것이다.

```html
<div class="game-root" style="position:relative; width:1920px; height:1080px;">
  <canvas class="battle-canvas" style="position:absolute; inset:0;"></canvas>
  <div class="ui-overlay" style="position:absolute; inset:0; pointer-events:none;">
     <!-- 상단 재화 스트립, 진행바, 버튼, 모달, 토스트 -->
     <div class="currency-strip" style="pointer-events:auto;">...</div>
     <div class="stage-progress-bar" style="pointer-events:auto;">...</div>
     <button class="skill-button" style="pointer-events:auto;">...</button>
  </div>
</div>
```

핵심 규칙:
- `ui-overlay` 컨테이너는 기본적으로 `pointer-events: none`으로 두어 클릭이 캔버스로 그대로 통과하게 하고, 실제 상호작용이 필요한 개별 요소(버튼, 모달, 카드)에만 `pointer-events: auto`를 다시 켠다. "빈 공간 클릭 시 캔버스로 전달 / UI 위 클릭 시 UI가 처리"가 자연스럽게 성립.
- 진행바 같은 요소는 캔버스 안에 그릴 필요 없이 DOM으로 오버레이하고 `width` 스타일만 갱신하면 됨(CSS transition으로 부드러운 채움 애니메이션도 공짜로 얻음).
- React/Vue를 쓴다면, **캔버스는 프레임워크 렌더 트리 바깥의 "탈출구(escape hatch)"**로 다룬다 — `useRef` + `useEffect`로 캔버스/Pixi Application을 한 번 마운트하고, 이후 프레임 갱신은 rAF/Pixi Ticker가 담당하며 virtual DOM 리렌더링과는 분리한다. HUD 텍스트(골드 숫자 등)처럼 "값이 바뀔 때만" 갱신하면 되는 부분은 일반 React state로 관리.
- 전투 루프(캔버스)와 React UI 사이의 상태 공유는 매 프레임 React를 거치지 않도록, 가벼운 외부 스토어(zustand/valtio, 혹은 직접 만든 pub-sub)를 두고 캔버스 루프와 React 컴포넌트가 각자 구독하는 패턴이 일반적.

이 패턴은 업계 표준이며, PixiJS를 쓰더라도 그대로 적용된다(Pixi의 `view`가 곧 `<canvas>` 엘리먼트이므로 동일한 레이어링 규칙 적용).

## 4. 최종 추천

**추천: PixiJS(전투 캔버스) + React 또는 Vue(HUD·성장보드·모달·토스트 등 나머지 UI 전부 DOM) 하이브리드 구조**

이유:
1. "초당 다수의 이펙트(타격 이펙트, 파티클, 크리티컬 텍스트)"는 PixiJS의 배칭 렌더링/파티클 컨테이너가 정확히 겨냥하는 시나리오. raw Canvas 2D로도 불가능한 건 아니지만, 이펙트 수가 늘어날수록 직접 짜야 하는 최적화(오브젝트 풀링, draw call 정렬)를 PixiJS가 상당 부분 대신 해준다.
2. "자동전투가 계속 돌아야 하고 배터리/CPU 부담이 크면 안 된다"는 조건에서, GPU 배칭 렌더링은 CPU 부담을 줄이는 방향으로 유리하다.
3. Phaser 3나 Three.js는 이 프로젝트가 필요로 하지 않는 기능(물리엔진, 타일맵, 3D 파이프라인)을 함께 끌고 오므로 소규모 개발 리소스 대비 비효율적이다.
4. 성장보드/HUD/팝업/토스트는 캔버스가 아니라 DOM으로 처리하는 것이 개발 속도, 접근성, 클릭/호버 처리 측면에서 압도적으로 유리하다. Konva는 좋은 라이브러리지만, 이미 React/Vue를 쓴다면 성장보드 정도의 노드 그래프는 순수 DOM+SVG로도 충분하고 별도 캔버스 라이브러리를 하나 더 들이는 비용을 아낄 수 있다.
5. UI 프레임워크(React/Vue) 병행에 대한 의견: **병행을 권장**. UI 요소(재화 스트립, 모달, 토스트, 트리 카드 팝업)의 비중이 커서, 프레임워크 없이 DOM을 직접 조작하면 상태 관리가 금방 지저분해진다. 다만 "캔버스는 프레임워크 렌더 트리 밖에서 rAF/Ticker로 독립 구동"하는 패턴을 지켜서, 매 프레임 리렌더링이 도는 일이 없도록 해야 한다. React든 Vue든 큰 차이는 없으며, 팀의 기존 익숙도로 결정.

대안으로 남겨둘 것: "라이브러리 의존성 자체를 최소화하고 싶다"거나 이펙트 볼륨이 생각보다 훨씬 적다면(초당 파티클 수십 개 이하) raw Canvas 2D + DOM 하이브리드도 충분히 실용적인 선택지다. 이 경우 번들 크기와 학습 대상이 더 줄어드는 대신, 파티클 풀링과 배칭을 직접 구현해야 한다.

## 5. 다음 단계 제안 (프로토타입 시작 시)

1. **기본 스캐폴드 구성**: Vite + React(or Vue) + PixiJS로 프로젝트를 세팅하고, `game-root` div 안에 1920x1080 크기의 PixiJS `Application`을 마운트하는 컴포넌트 하나를 만들어, 스프라이트 하나가 Ticker로 움직이는 최소 예제부터 확인한다.
2. **전투 씬 뼈대 구현**: 스프라이트시트(텍스처 아틀라스)를 로드해 두 캐릭터의 idle/attack 애니메이션 상태머신을 만들고, 타격 이펙트·크리티컬 텍스트 팝업용으로 간단한 오브젝트 풀(또는 `@pixi/particle-emitter`)을 붙여 "초당 다수 이펙트"가 실제로 감당 가능한지 프레임레이트를 확인한다.
3. **레이어링/성장보드 스켈레톤 검증**: 캔버스 위에 진행바와 버튼 하나를 DOM으로 오버레이해 `pointer-events` 패턴이 의도대로 동작하는지 확인하고, 병행해서 성장보드를 더미 노드 10~20개짜리 DOM+SVG 트리로 프로토타이핑해 클릭→카드 팝업 흐름을 검증한다.
